# PROJ1-1-1 Discovery — 방향 확정

- 티켓: PROJ1-1-1 / P0 결함 3건 수정
- 작성일: 2026-09-04
- 근거: 2026-09-04 코드베이스 전수 분석(53파일 / 10,823 LOC 정독)

## 1. 목표 (Why)
전수 분석에서 도출된 P0 3건은 각각 (a) 사용자가 실제로 누르는 버튼에서 앱이 죽고,
(b) 산출물인 엑셀에 중복 행이 들어가며, (c) 배포된 앱에서 지오코딩 기능 전체가
동작하지 않는, **이미 깨져 있는** 결함이다. 신규 기능이 아니라 회귀 복구가 목적이다.

## 2. 사용자 (Who)
봉화군 농업기술센터 담당자 1인 내외. GitHub Pages에 배포된 정적 웹앱을 브라우저에서
사용한다. 즉 프로덕션 = GitHub Pages 빌드이며, dev 서버 프록시에 의존하는 경로는
사용자에게 도달하지 않는다.

## 3. 범위 (What)
포함 — P0 3건만.
- P0-1 `src/pages/ReviewPage.tsx`, `src/pages/ExportPage.tsx` (Hooks 순서)
- P0-2 `src/store/extractionStore.ts` (대표필지 중복 병합)
- P0-3 `.github/workflows/deploy.yml`, `src/lib/kakaoGeocoder.ts` (프로덕션 키/경로)

제외 — P1(정렬 난수, parcelId 고유키, 면적 파싱, 검증 대상, 먼 리 임계값, PNU 컬럼),
P2(키 노출, xlsx CVE), P3(테스트 도입, 죽은 코드, DRY). 별도 티켓으로 후속 처리.

## 4. 제약
- 파일 충돌 금지: 서브에이전트 3개가 병렬로 일하므로 위 파일 집합은 서로 겹치지 않는다.
- 리팩터링 금지: P0 수정에 필요한 최소 변경만. 동작 변경 범위를 좁게 유지해야 회귀 판정이 쉽다.
- 테스트 프레임워크가 없으므로 검증 수단은 `npm run build`(tsc -b && vite build) + 코드 리뷰.

## 5. 우선순위
P0-1 > P0-2 > P0-3. 크래시 > 산출물 오염 > 기능 불능 순.
다만 세 건은 파일이 분리되어 있어 병렬 실행하며, 순서는 리뷰 시 심각도 정렬에만 쓴다.

## 6. 리스크
- P0-2: `repDirect` → `repNotInPublic` 교체가 "적격 대표필지 전부 포함" 정책을 바꾸는 것으로
  오해될 수 있다. 실제로는 공익직불제 시트에 이미 들어간 건을 대표필지 시트에 또 넣지 않는
  것이며, 총 커버리지는 동일하다. 로그 문구도 함께 맞춰야 한다.
- P0-3: 프로덕션에서 Kakao REST를 CORS로 직접 호출할 수 없다는 사실은 변하지 않는다.
  이번 범위는 "VWorld 키를 배포 빌드에 전달" + "동작하지 않는 Kakao 경로를 프로덕션에서
  가용 판정에 넣지 않기"까지다. 서버 프록시 도입은 P2로 미룬다.
- 훅 순서 수정 시 early return 이후에 있던 지역 변수 참조 순서가 깨질 수 있다.

## 7. 검증
- `npm run build` 통과 (타입 + 번들)
- P0-1: ExportPage에서 result가 null로 전이될 때 훅 개수가 불변임을 코드로 확인
- P0-2: 병합 결과에 동일 matchKey가 2회 등장하지 않음을 코드 경로로 확인
- P0-3: `dist/assets/*.js`에 VWorld 키가 주입되는 빌드 경로 확인, deploy.yml diff 확인
- 독립 리뷰: critic(플랜) + code-reviewer(코드) + codex(다른 계열 모델 diff 리뷰)
