## 2. 먼 리 임계값이 중위값 — 리의 절반이 항상 제외된다

```ts
const sorted = [...dists].sort((a, b) => a - b);
const median = sorted[Math.floor(sorted.length / 2)];
threshold = median;
```

중위값은 **정의상 절반을 넘긴다.** 리가 아무리 모여 있어도 절반이 잘린다.

### 실측 — VWorld 연속지적도로 봉화군 71개 리의 실제 중심 계산

각 리의 필지 폴리곤 중심점을 평균해 리 중심을 구하고, 전체 중심으로부터의
거리 분포를 쟀다.

```
거리 범위 0.8 ~ 26.8km, 평균 11.4, 표준편차 5.6, 중위값 10.5

평균+2σ = 22.6km → 제외  2개 리
중위값  = 10.5km → 제외 35개 리   ← 대표필지가 있을 때 쓰던 값
```

중위값 기준으로 잘려나가던 리에는 **상리(10.9km), 눌산리(11.1km), 삼계리(11.1km)**
같은 평범한 거리의 리가 포함된다. 봉화군 중심에서 11km는 "먼 리"가 아니다.

즉 **대표필지 파일을 넣는 순간 봉화군 리의 절반이 통째로 추출 대상에서 사라졌다.**

### 기준이 두 개로 갈라져 있던 것도 문제였다

대표필지가 없는 경로(`spatialUtils.findDistantRis`)는 이미 `평균 + 2σ`를 쓰고
있었다. 같은 "먼 리 판정"인데 대표필지 유무에 따라 기준이 달랐다.

### 조치

`meanPlusTwoSigma`를 `spatialUtils`에 두고 두 경로가 공유한다.
중위값을 쓰지 말아야 하는 이유와 실측 수치를 함수 주석에 남겼다.

## 3. 검증이 최종 결과와 다른 대상을 본다

`runExtraction`은 `totalTarget`을 `publicPaymentTarget`으로 덮은 `effectiveConfig`로
`extractParcels`를 호출한다. 따라서 `result.validation`은 **공익직불제 필지만**
담긴 배열과 공익직불제 목표를 기준으로 계산된다.

그런데 store는 `selectedParcels`만 병합 결과로 갈아끼운다.

```ts
set({ result: { ...result, selectedParcels: finalParcels } });
//                          ^^^^^^^^^^^^^ 대표필지까지 병합
//              ^^^^^^^^^^^ validation은 공익직불제 기준 그대로
```

화면에는 병합 결과가 뜨는데 경고는 공익직불제 기준이라 숫자가 어긋난다.

### 조치

병합 후 `validateExtraction`을 다시 호출한다. 대상은 `dedupeSelected(finalParcels)`이다.
UI가 `countUniqueSelected`로 겹침을 1건으로 세므로 검증도 같은 기준이어야 한다.

> ⚠️ 초안에서는 목표로 `config.totalTarget`을 썼다. **그것이 틀렸고**, 5절에서
> 실행 기준으로 역산하도록 고쳤다.

이를 위해 `validateExtraction`을 export로 바꿨다.

## 6. 업무 규칙이 확정되면서 설계가 바뀌었다

재리뷰 중 사용자가 물었다. **"공익직불제에 대표필지가 포함되는 거 맞아?"**

실측해보니 코드가 대표필지를 **두 번 넣고 있었다.**

```
대표필지 10건(마스터에도 있는 필지)을 넣으면
  공익직불제 100행 + 대표필지 10행 = 110행
  고유 필지 100건
  같은 필지가 2행: 10건 → [public-payment, representative]
```

두 단계가 겹쳐서다.

1. `extractFromRi`가 `repParcelKeys`로 대표필지를 **공익 추출에 우선 포함**시킨다
2. 그 뒤 `repDirect = enrichedEligibleRep.map(...)`가 적격 대표필지 **전부**를 다시 넣는다

결과적으로 대표필지가 공익 700자리를 차지하면서 대표필지로도 계산됐다. 어느 규칙에도
맞지 않는 상태였다.

| 규칙 | 기대 | 당시 코드 |
| --- | --- | --- |
| 대표필지 별도 쿼터 (700 + N) | 공익 700을 잠식하면 안 됨 | 잠식함 |
| 대표필지가 총 700에 포함 | 또 추가하면 안 됨 | 또 추가함 |

### 확정된 규칙: **총 700 안에 대표필지 포함**

```
공익직불제 목표 700
  ├─ 대표필지  30건 (우선 선택, 고정 관측점)
  └─ 신규 추출 670건
최종           700건
```

### 조치

**공익에 이미 뽑힌 대표필지는 태깅만 한다.** 행을 새로 만들지 않는다.

```ts
const taggedPublic = result.selectedParcels.map(p => {
  const isRep = repParcelKeys.has(matchKey(p)) || (fk && repParcelKeys.has(fk));
  return isRep ? { ...p, parcelCategory: 'representative' as const } : p;
});
const repDirect = repNotInPublic.map(...);   // 안 뽑힌 것만 추가
```

**목표를 넘으면 비대표 필지를 덜어낸다.** 대표필지는 고정 관측점이라 반드시
포함되어야 하고, 밀려나는 쪽은 신규 추출분이다. 뒤에서부터 제거하므로
밀집도·근접도 점수가 낮은 것이 먼저 빠진다.

**검증 목표도 단순해졌다.** 겹침이 없으므로 `effectiveTotal = publicTarget`이다.
앞서 만든 역산(`publicTarget + repNotInPublic + repSupplements`)은 겹침을 전제한
것이라 더 이상 필요 없다.

### 검증

| 시나리오 | 결과 |
| --- | --- |
| 대표필지가 공익에도 뽑힘 | **100건 / 고유 100 / 겹침 0** — 태깅만 |
| 대표필지가 공익에 안 뽑힘 | **100건 유지** — 신규 20건 제외, 대표 20건 전부 포함 |
| 대표필지가 목표 초과(120 > 100) | 120건 + 경고 — 물리적으로 불가피 |

### 재리뷰 — 내가 새로 만든 HIGH 결함

재설계 후 리뷰가 **이번에 새로 들어온 결함**을 잡았다.

**HIGH-1 — 초과분 제거가 마지막 리를 통째로 날렸다**

`merged`는 점수 내림차순이 아니다. `extractParcels` Step 3이 **리 단위로 순차
push**하므로, "뒤에서부터"는 "점수가 낮은 것부터"가 아니라 **"마스터에 늦게
등장한 리부터"**였다.

더 결정적으로 Step 3에는 총 목표 상한이 없다. 리마다 `perRiTarget`을 무조건
채우므로 **리 71개 × 10 = 710 > 목표 700**이 되고, 그 초과 10건을 뒤에서
자르면 마지막 리의 배정분이 통째로 사라진다.

내가 검증한 세 시나리오는 모두 `리 수 × perRiTarget == 목표`라 이 경로를
밟지 않았다. 실데이터에서는 반드시 밟는다.

→ **리별 초과분부터** 라운드로빈으로 덜어내도록 고쳤다. 목표 대비 초과가 큰
리에서 한 건씩 돌아가며 빼고, 각 리 안에서는 뒤쪽부터 뺀다.

**HIGH-2 — 확정 규칙이 UI에 반영되지 않았다**

스토어만 고치고 화면은 그대로 뒀다. `ExtractionSettings`가
`totalTarget = public + representative`를 유지해, 결과 700건인데 화면은
**"선택: 700 / 750"**으로 떴다. 사용자는 여전히 가산 쿼터로 이해한다.

→ `totalTarget = publicPaymentTarget`으로 통일하고, "대표필지는 이 안에
포함됩니다" 안내를 붙였다. `ExtractPage`의 "목표 700개를 그대로 추출합니다"도
"목표 안에 우선 포함되며 그만큼 신규 추출분이 줄어듭니다"로 고쳤다.

**함께 반영한 MEDIUM**

| 검증·통계는 dedupe 배열, 화면·엑셀은 원본 → 숫자가 갈림 | `selectedParcels`도 dedupe 결과로 통일 |

## 7. 남은 것

- **`maxRiDistanceKm`를 사용자가 직접 지정하는 경로는 그대로다.** 자동 계산
  (`0`일 때)만 바꿨다. 절대 거리 기준을 기본값으로 제시할지는 별건.
- **`representativeTarget`이 상한으로 쓰이지 않는다.** `0 = 전부 포함`이라는

  80건이면 80건이 전부 들어간다. 이번에는 목표를 실행에서 역산해 검증만
  맞췄고 동작은 그대로 뒀다. 상한으로 쓸지는 업무 결정이라 별건.
