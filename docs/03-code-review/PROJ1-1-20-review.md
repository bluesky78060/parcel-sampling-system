### 3-1. 4번을 그대로 받지 않은 이유

VWorld는 **과부하 상황에서도** "인증키 정보가 올바르지 않습니다"를 돌려준다(이전 세션에서 실측).
메시지만으로 영구 실패와 일시 부하를 구분할 수 없으므로, 한 건도 성공하지 못한 상태에서만
영구 실패로 판단해 중단하기로 했다.

> ⚠️ **이 1차 조치 자체가 결함이었다.** `snappedCount === 0`은 콜드 스타트 첫 청크에서
> 반드시 참이고, 재시도를 쓰기 전에 판정해 버려 오히려 전량 실패 경로를 만들었다.
> 7절 MAJOR 2 참조.

### 3-2. 2번을 지적보다 넓게 고친 이유

gemini는 위도 하한만 지적했으나, 실측해 보니 **경도 상한(129.25)도** 소천면 필지를 자르고 있었다
(실측 최대 129.37416). 표본 14,400건 중 60건(0.42%)이 기존 범위 밖이었다.

## 4. 적대적 검증 — 콜드 캐시 실행

가장 중요한 검증이다. 이전 실행은 IndexedDB에 30,684건이 이미 있는 **캐시 워밍 상태**여서
1번 결함(캐시 상한)을 가리고 있었다. `geocode-cache`를 비우고 처음부터 돌렸다.

```
[PNU 스냅] 리 72개 / PNU 32,461건
  4792038022: 490/490
  4792036024: 622/622
  4792034026: 789/789
  ...
  완료: 32,435/32,461건 스냅
Phase 0 완료: PNU 32,461종으로 38,958건 좌표 확보 (119.6초)
Phase 1 완료: 26건, 성공 3건, 실패 23건 (1.9초)
전체 완료 (121.5초): PNU 38,958건 + 주소 3건 = 38,961/38,984건 성공, 실패 23건
```

| | |
| --- | --- |
| 전체 | 38,984건 (2027원본+원본2, 봉화군 밖 제외 후) |
| PNU로 해결 | **38,958건 (99.93%)** |
| 주소 폴백 | 3건 |
| 실패 | **23건 (0.06%)** |
| 소요 | **121.5초** |

수정 후 재현 실행에서도 130초 / 38,961건으로 동일했다.

### 캐시 상한 수정이 없었다면

`prefetchPolygonsByPnu`는 `cacheSet`으로 스냅 결과를 넣는데 상한이 10,000이었다.
32,461종을 스냅하면 앞선 22,000여 건이 LRU로 축출되고, Phase 0 직후
`getSnappedCoord`로 회수할 때 `null`이 되어 주소 폴백으로 떨어진다.
`warmupCache`만 `geocodeCache.set`을 직접 써서 상한을 우회하고 있었기 때문에
**두 번째 실행에서는 정상 동작해 결함이 숨었다.**

## 7. code-reviewer(Claude Opus) 리뷰 — REQUEST CHANGES 및 반영

첫 레인이 MAJOR 3건을 잡았다. 셋 다 재현 경로가 명확해 전부 반영했다.

### MAJOR 1 — `force=true` 재변환이 조용히 무력화됨

```ts
const needsAddress = needsGeocode.filter(idx => !results[idx].coords);
```

`results`는 입력 필지의 **기존 좌표를 그대로 들고 있다.** `force: true`면 좌표가 이미 있는
필지도 `needsGeocode`에 들어가는데, Phase 0가 해결하지 못하면 낡은 좌표가 truthy라
Phase 1 대상에서 빠진다. 「좌표 재변환」을 눌러도 고쳐지지 않는 필지가 생기고,
그 건수는 성공에도 실패에도 잡히지 않아 통계까지 어긋난다.

→ `pnuResolvedIdx: Set<number>`로 Phase 0 해결 여부를 명시적으로 추적하도록 바꿨다.

### MAJOR 2 — 내가 넣은 인증 fast-fail이 오히려 위험을 만들었다

`attempt === 0`에서 곧바로 `return`해 백오프를 한 번도 쓰지 않았다. `snappedCount`는
콜드 스타트 첫 청크에서 반드시 0이므로, **VWorld가 과부하인 순간에 좌표 변환을 시작하면
첫 3개 요청만으로 Phase 0 전체가 0건으로 끝난다.** 0패딩 파일이면 주소 폴백도 전멸해
39,000건 전량이 좌표 없이 끝나는데 UI에는 "완료"로 보인다.

3-1에서 "성공 이력이 있으면 재시도를 유지한다"고 적어놓고, 정작 성공 이력이 쌓일 수 없는
시작 시점에 유예를 0으로 만든 셈이다.

→ 판정을 **재시도 소진 이후**로 미루고, 서로 다른 리 2개(`AUTH_FAIL_RI_THRESHOLD`)가
같은 이유로 죽었을 때만 접도록 고쳤다.

### MAJOR 3 — 미매칭 PNU 네거티브 캐시 부재 (재실행 회귀)

`uncached`가 성공한 PNU만 제외해서, 리 조회가 정상적으로 끝났는데도 매칭되지 않은 PNU가
어디에도 기록되지 않았다. 미해결 23건이 남은 상태에서 지도 탭의 「좌표 변환」을 누르면
그 23건이 흩어진 리를 **통째로(리당 최대 4,356필지) 다시 내려받고 0건을 얻는다.**
기존 주소 방식에서는 23회 조회로 끝나던 흐름이라 명백한 회귀다.

→ 조회 자체가 성공한 리에서 끝까지 안 나온 PNU는 `pnuFailCacheAdd`로 기록하고
`uncached` 필터에 반영했다.
