# PROJ1-1-25 — VWorld 장애 시 조기 중단 + 원인 전달

작업일: 2026-09-06
브랜치: `bluesky78060/codebase-analysis`

## 문제

2026-09-06, 사용자가 프로덕션(GitHub Pages)에서 4만 필지 좌표 변환을 실행하던 중:

```
좌표 변환 중... 6,816/40,022 (17%)
변환 실패: 6,816건
```

처리 건수와 실패 건수가 정확히 같다 — 성공률 0%. 원인은 VWorld API 서버 장애였다.

```
Data API      → HTTP 502 / 000 (연결 실패)
지오코딩 API   → HTTP 502
www.vworld.kr → HTTP 200   (메인 사이트만 정상)
```

앱은 두 가지를 하지 못했다.

1. **조기 중단**: PNU 경로와 주소 폴백이 동시에 죽었는데도 4만 건을 끝까지 시도했다.
2. **원인 전달**: 화면에 "변환 실패 N건"만 떠서, 사용자가 자기 데이터 문제인지 서버 문제인지
   구분할 수 없었다. 그래서 계속 재시도하며 죽은 서버에 부하만 더했다.

### 왜 기존 fast-fail이 안 걸렸나

PROJ1-1-20에서 인증 오류 fast-fail을 넣어 두었다.

```ts
if (isAuthError(text) && snappedCount === 0) { ... }
```

**502는 이 경로를 타지 않는다.** VWorld는 CORS 헤더를 보내지 않아 JSONP(script 태그)로
호출하는데, 502는 응답 본문이 아니라 `script.onerror`로 나타난다. 즉 `text`가 존재하지 않고,
JSONP 네트워크 오류로 분류되어 리마다 재시도 3회를 조용히 소진했다.

같은 이유로 **HTTP 상태 코드를 읽을 수 없다.** 502인지 503인지 DNS 실패인지 구분이 불가능하므로,
사용자 문구에 특정 상태 코드를 적지 않았다(티켓 초안은 "HTTP 502"를 명시하라고 했으나,
그렇게 쓰면 확인할 수 없는 사실을 단정하는 것이 된다).

## 변경 내용

### 1. `GeocodeServiceError` — "좌표 없음"과 "서버 미응답"의 분리

`geocodeVworld`가 네트워크 오류를 삼키고 `null`을 반환하고 있었다. 호출자는 그것을
"이 주소에는 좌표가 없다"로 받아들였다. 이것이 4만 건을 끝까지 돌게 만든 직접 원인이다.

지번·도로명 두 경로가 **모두** 서버 미응답으로 끝났을 때만 던진다. 한쪽이라도 응답했다면
데이터 문제이므로 종전대로 `null`이다.

### 2. 조기 중단의 사유 일반화

`AUTH_FAIL_RI_THRESHOLD` → `SERVICE_DOWN_RI_THRESHOLD`. 인증 오류든 502든 타임아웃이든
**성공 0건 상태에서 서로 다른 리 2개가 죽으면** 중단한다.

한 건이라도 스냅에 성공했다면 서버는 살아 있는 것이므로 개별 리의 문제로 보고 계속 진행한다
(`recordRiFailure`가 `snappedCount > 0`이면 장애 집계에서 빠진다).

Phase 1(주소 폴백)에도 같은 가드를 넣었다 — 성공 0건인 채로 서버 미응답 배치가 2개 연속이면 중단.

### 3. 사전 헬스체크

`checkGeocodingService()`. 변환 시작 전 1건(`size=1`, 타임아웃 8초)을 조회한다.

조기 중단만으로도 장애는 잡히지만 리 2개가 재시도(45초×3 + 백오프)를 소진해야 하므로
최악 4분이 걸린다. 헬스체크는 같은 사실을 8초 안에 알려준다.

### 4. 진단을 호출자에게 전달

- `prefetchPolygonsByPnu`: `number` → `PnuPrefetchResult { snapped, failedRi, serviceDown, failureKind, lastError }`
- `batchGeocode`: `Parcel[]` → `{ parcels, diagnostics }`
- `useGeocoding.state`: `serviceDown`, `notFound` 추가

**서버 장애일 때 `isComplete`를 true로 두지 않는다.** 전량 실패했는데 "좌표 변환 완료!"가
뜨는 것이 이번 장애에서 가장 큰 혼란이었다.

### 5. UI 문구 분리

| 상황 | 이전 | 이후 |
|---|---|---|
| 서버 장애 | 변환 실패: 6,816건 | 좌표 변환 중단 — 남은 필지는 시도하지 않았습니다 + 원인 + 다시 시도 버튼 |
| 좌표 못 찾음 | 변환 실패: 23건 | 좌표를 찾지 못한 필지: 23건 |

### 그 밖에 반영한 MEDIUM

- **Kakao 전용 dev 환경이 막혔다.** `isGeocodingAvailable()`은 Kakao 키만 있어도 true인데
  헬스체크는 VWORLD 키가 없으면 실패를 돌려줬다 → VWORLD 키가 없으면 헬스체크를 건너뛴다.
- **`failureKind='auth'` 고착.** VWorld는 과부하일 때도 인증키 문구를 돌려준다(이 저장소의
  기존 주석이 그렇게 적고 있다). 502 장애 중 리 하나가 그 문구를 받으면 사용자에게
  "인증키를 확인하라"고 안내하게 된다 — 사용자가 고칠 수 없는 조치다.
  → 헬스체크가 통과했다면 키는 유효하므로 `unreachable`로 강등한다.
- **Phase 0 장애 시 주소 폴백을 건너뛰던 것을 되돌렸다.** Data API만 죽고 지오코딩 API는
  살아 있을 수 있고, 재개 실행처럼 조회 대상 리가 두어 개뿐이면 그 둘의 실패가 곧 서버 장애를
  뜻하지도 않는다. Phase 1의 가드가 몇십 건 안에 실제 생존을 판정한다. 주소로 좌표를 얻으면
  Phase 0가 세운 장애 판정을 거둔다.
- **`notFound`가 상태까지 오고 화면에서 쓰이지 않았다.** UI는 여전히 `failed`(= notFound +
  서버 미응답)를 쓰면서 라벨만 바꿔, 서버 미응답까지 데이터 문제로 단정했다 → 두 수를 나눠 표기.

### 리뷰 대응 중 스스로 찾은 것

**`clearGeocodeCache()`가 IndexedDB 삭제를 기다리지 않았다.**

```ts
clearGeocodeCache();          // clearIDBCache()를 fire-and-forget
geocoding.resetState();
await geocoding.startGeocoding(parcels, true);   // 곧바로 warmupCache() → loadAllFromIDB()
```

삭제가 끝나기 전에 `warmupCache()`가 돌면 **낡은 좌표를 다시 읽어 들인다.** 예전에는 캐시
회수가 `prefetchPolygonsByPnu` 뒤에 있어 창이 좁았지만, 캐시 회수를 네트워크보다 앞으로
옮긴 지금은 그 낡은 값이 **곧장 결과가 된다.** "캐시 초기화 및 좌표 재변환" 버튼이 하는
일이 정확히 이것이므로 그대로 두면 안 된다.

→ `clearGeocodeCache()`를 `async`로 바꾸고 `AnalyzePage.rerunGeocoding`에서 `await` 한다.
`parcelStore.reset()`은 zustand action이라 동기여서 기다릴 수 없지만, reset 직후 지오코딩을
시작하는 경로가 없어(파일 업로드부터 다시 한다) 경합이 문제되지 않는다 — `void`로 의도를 밝혔다.

직전 티켓(PROJ1-1-5)에서 리뷰 지적을 고친 뒤 **재리뷰 없이 머지**했다가, 사후 확인 리뷰에서

앞서 의심 항목으로 넘긴 6가지(청크 경계 경합, 판정 되돌림 조건, `force=true` 경로,

조기 중단의 심장부(청크 경계 판정)는 반증을 견뎠지만, **그것을 감싼 바깥층 세 곳**이 깨져 있었다.

권한은 가장 공격적인(단판·재시도 없음) 헬스체크가 쥐고 있다. 두 층의 보수성이 정반대다."

`catch`에 삼켜져 여전히 1,006요청이 나갔다. `RateLimitError`·`AbortError`만 rethrow하고 있었던
것이다. 단정이 없었다면 표를 눈으로 훑고 넘어갔을 것이다.

반증에 실패한 항목(무너뜨리려 했으나 견딘 것)도 명시적으로 기록됐다 — 청크 경계 경합,
취소 시 판정 되돌림, "4만 건 중 1건만 성공", `force=true` + 캐시 회수 순서, `onProgress`의
total 초과, `AbortError` 카운터 정합성, `failed - notFound` 음수 가능성, 저장소 시나리오 9개.

### 그 밖에 반영한 Minor

### 4라운드 (critic 재재리뷰) — ACCEPT-WITH-RESERVATIONS

N1~N4와 단정 보강은 전부 닫혔음이 독립 재현으로 확인됐다(리뷰어가 직접 빌드·실행).
남은 MAJOR 1건:

**M1 — 한 필지가 `quotaBlocked`와 `unreachableTotal` 양쪽에 계상됐다.**

```ts
if (rateLimited) { chunkQuota += n; quotaBlocked += n; }   // 무조건 실행
...
if (coords === null) {
  if (unreachable)      { unreachableTotal += n; }          // unreachable 우선
  else if (rateLimited) { /* 위에서 이미 셌다 */ }
  else                  { notFound += n; }
}
```

`unreachable`은 성공했을 때만 false로 돌아가므로, attempt 0이 네트워크 미응답이고 attempt 1이
한도 초과로 끝난 필지가 양쪽에 들어간다. 그런데 화면은 미응답 건수를
`failed - notFound - quotaBlocked`라는 **뺄셈으로 유도**하고 있어, 이중 계상된 만큼 조용히
깎여 **"서버 미응답" 줄이 통째로 사라졌다.** 헤드라인은 "잠시 후 다시 시도하세요", 목록은
"한도가 초기화된 뒤에"가 한 화면에 동시에 떴다 — N3이 없앴던 모순이 다른 경로로 재현됐다.

`max(0, …)` 가드가 있어 안전한 것이 아니었다. 리뷰어 지적대로 **음수는 구조적으로 불가능**해서
그 가드는 한 번도 발동하지 않고, 대신 불일치를 숨기고 있었다.

조치:
1. 실패 사유를 **하나의 배타 체인**으로(`rateLimited` → `authRejected` → `unreachable` → `notFound`).
   플래그도 서로를 끄게 했다 — 서버가 한도를 알려줬다면 살아 있다는 뜻이므로 앞선 미응답 판정을 덮는다.
2. **뺄셈 제거.** `diagnostics`에 `unreachable`·`authBlocked`·`attemptedFailures`를 실어 화면이 받아쓴다.
3. 실패 목록에 **인증 거부 칸** 추가(Minor) — 없어서 "서버 미응답 — 다시 실행하면 재시도합니다"로 나왔다.
4. Phase 0 사유 판정도 **카운트 기반**으로(Minor) — `if (kind === 'auth' || …)`는 quota 도입 전 규칙이라
   리1이 한도·리2가 인증이면 한도가 묻혔다.

리뷰어가 짚은 공통 패턴이 이번 티켓의 교훈이다.

> **파생값을 뺄셈으로 만들면 "원본이 파티션"이라는 가정이 코드 어디에도 검사되지 않는다.**
> F3(추정치에서 성공 건수 유도), N3(뺄셈으로 미응답 유도), M1이 전부 같은 패턴이다.

그래서 사람의 리뷰 라운드를 한 번 더 도는 대신 **자동 불변식**으로 옮겼다.
시뮬레이터에 `notFound + quotaBlocked + unreachable + authBlocked === attemptedFailures`를
무조건 검산으로 넣었다(`expect` 없이 전 시나리오에서 실행).

**변이 검증**: M1 수정만 역치환한 트리를 같은 하네스로 돌려 **종료코드 1, 시나리오 14·15 실패**.
나머지 14건은 통과했으므로 검산이 M1에만 반응하고 과민하지 않다.

### 4라운드에서 견딘 것

리뷰어가 지난 라운드 공격 시나리오를 전부 재실행해 확인했다.
- **F1 완화는 과하지 않았다** — 진짜 키 사고(데이터·지오코딩 모두 거부)에서 `serviceDown=true`,
  **111요청 / 3.44초**(Phase 0가 3.0초에 판정). 헬스체크 차단보다 2.8초·100요청이 교환 비용의 전부다.

### 5라운드 (code-reviewer, M1 수정분 확인) — HIGH 1건

critic이 "전체 재리뷰 대신 M1 diff만 다른 사람이 눈으로 확인하라"고 한 데 따른 것이다.
460줄만 봤는데 결함이 하나 더 나왔다.

**성공한 재시도가 `authRejected`를 거두지 않았다.**

```ts
coords = await geocodeAddress(parcel.address);
unreachable = false;      // ← unreachable만 거둔다
break;
```

`geocodeAddress`는 "좌표 없음"을 throw가 아니라 `null` 반환으로 알리고 그 경로도 이 `break`를
탄다. 그래서 **attempt 0이 인증 오류 → attempt 1이 정상 "결과 없음"** 인 필지는 `authRejected`가
참인 채로 배타 체인에 들어가 `authBlocked`로 집계된다.

파급이 표시 오류에서 끝나지 않는다. `chunkNotFound`가 오르지 않으므로 `sawResponse`가 거짓이
되고 `chunkServiceError`가 오르므로 `batchDead`가 참이 된다 — **정상 응답한 배치가 죽은 배치로
판정되어 조기 중단이 걸린다.** 바로 그 코드가 주석에서 "절대 일어나면 안 된다"고 못 박은 오탐이다.

실측(500필지, attempt 0의 지번 호출만 `INVALID_KEY`, 이후 전부 정상 `NOT_FOUND`):

| | 수정 전 | 수정 후 |
|---|---|---|
| serviceDown | **true** | false |
| failureKind | **auth** | – |
| notFound | **0** | 500 |
| authBlocked | **50** | 0 |
| 시도한 필지 | **50 (450건 포기)** | 500 |

화면에는 "VWORLD가 인증키를 거부했습니다 … 배포 키를 확인해야 합니다" + 450건 포기가 뜬다.
키는 멀쩡하다. 트리거도 이국적이지 않다 — 이 저장소 주석이 세 군데에서 "VWORLD는 과부하일 때도
인증키 문구를 돌려준다"고 적고 있고, 간헐적 인증형 오류 + 좌표 없는 주소가 섞인 파일이면 성립한다.

**그리고 합계 불변식이 이것을 잡지 못했다.** `0+0+0+50 === 50`으로 파티션은 성립한다.

> 보존식은 **이중 계상만** 잡을 뿐 **오분류는 잡지 못한다.**

"남은 위험을 자동 불변식으로 옮긴다"는 전략의 사각지대다. 그래서 불변식과 별개로
**행동 시나리오**를 추가했다(리뷰어가 초안을 준 것을 그대로).

조치:
1. 성공 경로에서 `unreachable`·`authRejected`·`rateLimited`를 **모두** 거둔다(3줄).
2. 행동 시나리오 추가 — `expect: { serviceDown: false, notFound: TOTAL }`.
3. (MEDIUM) `attemptedFailures`를 화면까지 배선하고 `breakdown`의 분모를 `progress.failed`에서
   그 값으로 교체. 시뮬레이터가 검산하는 등식과 화면이 판정하는 등식이 달랐다 — 오늘 우연히
   일치할 뿐 보장이 없었다.
4. (LOW) 도달 불가 분기 `sawAuthError && unreachableTotal === 0`과 쓰기 전용 변수 제거,
   `!breakdown`일 때 `console.warn`, 고아 주석 이동, 중복 주석 통합.

**변이 검증**: 3줄만 역치환한 트리에서 **종료코드 1, 그 시나리오만 실패**
(`serviceDown true (기대 false)`, `notFound 0 (기대 500)`). 나머지 16건은 영향 없다.

## 남긴 판단

- **헬스체크를 선택 사항으로 두지 않았다.** 티켓은 "(선택)"으로 표시했으나, 조기 중단만으로는
  최초 감지에 최악 4분이 걸린다. 정상 경로 비용은 요청 1회이고, 캐시로 전량 해결되는 실행에서는
  아예 호출하지 않는다. 오탐 위험은 재시도 2회 + 타임아웃 통과로 낮췄다.
- **문구에 HTTP 상태 코드를 넣지 않았다.** JSONP는 상태 코드를 읽을 수 없다(위 참조).
- **`skipHealthCheck`는 시뮬레이터 전용이다.** UI에 "무시하고 계속"을 노출할지는 실사용에서
  오탐이 실제로 관측된 뒤에 판단한다. 지금 넣으면 사용자가 장애 중에도 4만 건을 태우는
  경로를 스스로 열게 된다.
- **실제 VWorld 응답 지연은 측정하지 않았다.** 하네스는 목(mock)이므로 헬스체크 8초 예산의
  타당성은 이 검증으로 뒷받침되지 않는다. 프로브를 리 하나로 좁히고 타임아웃을 통과 처리한
  것이 그 불확실성에 대한 대비다.
