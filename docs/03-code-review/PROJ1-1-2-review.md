## 1. 티켓의 진단과 실측 결과가 갈렸다

티켓은 두 결함을 "재현성 상실"과 "스택 오버플로"로 규정했다. 실제로 재현해 보니
**둘 다 진단이 정확하지 않았고, 대신 더 심각한 문제가 드러났다.**

| 티켓의 주장 | 실측 결과 |
| --- | --- |
| `randomSeed`를 고정해도 결과가 재현되지 않는다 | **단일 V8 빌드 안에서는 재현된다.** 수정 전 코드도 동일 시드 2회 실행이 완전 일치. 다만 브라우저·엔진이 바뀌면 실제로 깨진다(2-1 참조) |
| `Math.min(...arr)`가 수만 개에서 스택을 넘긴다 | 넘긴다. 단 **130,000개부터**이고, 봉화군 리당 최대 4,356필지라 실사용에서는 발동하지 않는다 |
| 비교자 내 재계산으로 지오코딩보다 느려질 수 있다 | 차이 없음. 30,485건 기준 210ms → 204ms (측정 오차 범위) |
| — | **정렬이 사실상 작동하지 않고 있었다** (아래) |

### 왜 내 테스트에서는 재현성이 멀쩡했나

`extractParcels`는 호출마다 `createRng(seed)`로 새 RNG를 만든다. 같은 시드면 같은 난수
수열이고, V8의 `Array.sort`는 같은 입력에 대해 결정적이므로 비교 순서도 같다. 따라서
비교자 안에서 `rng()`를 불러도 **같은 엔진·같은 입력**이면 결과가 재현된다.

> ⚠️ **처음에 "티켓 주장이 사실이 아니다"라고 적었으나 그것은 과한 단정이었다.**
> 사실이 아닌 것은 "단일 V8 빌드 안에서 관측된다"까지다. 아래 2-1이 보여주듯
> 엔진이 바뀌면 실제로 다른 결과가 나온다. 이 프로젝트는 Electron이 아니라
> 브라우저 앱이므로 담당자가 Safari나 Firefox로 열 수 있다.

### 2-1. rng 소비량이 입력에 따라 흔들린다 (code-reviewer 실측)

구 비교자가 소비하는 난수 개수:

```
n=4356  오름차순 36,718 / 내림차순 34,367 / 무작위 38,331   (새 코드는 항상 4,356)
n=1000  오름차순  6,365 / 내림차순  6,385 / 무작위  7,755   (새 코드는 항상 1,000)
```

입력의 정렬 정도만 달라져도 소비량이 4천 회 넘게 흔들린다. 정렬 알고리즘이 다른
엔진(JavaScriptCore, SpiderMonkey)에서는 비교 횟수가 달라 **같은 시드로 다른 700필지가
나온다.** 새 코드는 항상 정확히 n회를 소비하므로 엔진과 무관하게 고정된다.

## 2. 진짜 결함 — 정렬이 순위를 만들지 못했다

비교자가 호출될 때마다 새 난수를 더하면 비교 결과가 **비추이적**이 된다
(`a<b`, `b<c`인데 `a>c`). 정렬 알고리즘은 추이성을 전제로 하므로 결과 배열이
정렬된 상태가 아니게 된다.

항목 2,000개로 직접 측정했다.

```
(구) 비교자 내 난수 : 인접 역전 1061/1999,  상위100 적중 35/100
(신) 사전 노이즈    : 인접 역전    0/1999,  상위100 적중 28/100
```

**인접한 두 항목의 53%가 순위가 뒤집혀 있었다.** 즉 "밀집도 높은 필지 우선,
대표필지 근처 우선"이라는 의도가 코드에 적혀 있었을 뿐 실제로는 지켜지지 않았다.

> 수정 후의 `0/1999`는 측정값이 아니라 **구성상 자명한 값**이다. 미리 계산한 키로
> 정렬하면 그 키에 대한 역전은 정의상 0이다. 정보를 담은 숫자는 수정 전의 1061뿐이고,
> 그것이 뜻하는 바를 정확히 쓰면 "정렬 품질이 나빴다"가 아니라
> **"비교자가 `Array.prototype.sort` 계약(비추이성·비대칭성)을 위반해 결과 순서에
> 의미가 없었다"**이다. 이번 수정의 성과는 **순서가 점수의 함수가 되었다는 것**이다.

상위100 적중률이 35→28로 내려간 것은 회귀가 아니라 노이즈 가중치
(1 − densityWeight = 0.3)가 이제 의도대로 반영되기 때문이다. 구 버전의 35는 정렬이
망가진 상태에서 나온 우연한 값이라 비교 기준이 되지 못한다.

## 3. 조치

### 3-1. 노이즈를 항목마다 1회만 부여

```ts
const scored = cluster.map(p => {
  ...
  const score = repProximity * repWeight + density * densityShare;
  const rank = score * spatialConfig.densityWeight
    + (rng() - 0.5) * noiseWeight;   // 필지당 1회, 절반 폭
  return { parcel: p, rank };
});
scored.sort((a, b) => b.rank - a.rank);  // 순수 비교자
```

`rng()` 호출 횟수가 필지 수와 같아지고 순서도 `map` 순서로 고정되므로,
정렬 알고리즘 구현과 무관하게 결정적이다.

#### 진폭 보존 — code-reviewer가 잡은 MAJOR

초안은 `(rng() - 0.5) * 2 * noiseWeight`였다. 예전 비교자의 노이즈는 **1회 추출**이지만
새 비교값에는 **두 항목 노이즈의 차**가 들어가므로, 같은 식을 쓰면 진폭이 2배가 된다.

| | 범위 | 표준편차 |
| --- | --- | --- |
| 구(비교자 내 1회) | ±0.300 | 0.173 |
| 초안(`* 2`, 차) | ±0.600 | 0.245 |
| **반영본(`* 2` 제거, 차)** | **±0.300** | 0.123 |

`densityWeight`는 사용자가 슬라이더로 조절하는 값이라, 같은 0.7이 다른 무작위성을
뜻하게 되면 안 된다. `* 2`를 빼서 범위를 복원했다.

#### 지켜야 할 것은 표준편차가 아니라 지지집합이다

재리뷰가 더 정확한 근거를 제시했다. 중요한 것은 **점수 격차 g가 얼마일 때 노이즈가
순위를 뒤집을 수 있는가**이고, 그것이 슬라이더의 실질적 의미다.

| 점수 격차 g (noiseWeight 단위) | 구(균등) | 반영본(삼각 ±w) | 초안(삼각 ±2w) |
| --- | --- | --- | --- |
| 0.50 | 0.500 | 0.250 | 0.563 |
| 1.00 | **0** | **0** | **0.250** |
| 1.50 | **0** | **0** | 0.063 |

`* 2`가 있으면 **격차가 노이즈 예산을 넘는 쌍도 25% 확률로 뒤집힌다.** 구 코드에는
없던 동작이다. 반영본은 "격차 > noiseWeight면 절대 안 뒤집힌다"는 경계를 정확히
복원한다. 표준편차 일치보다 이 경계 보존이 슬라이더 의미상 훨씬 중요하다.

표준편차가 1/√2배(기본값 0.7에서 0.173 → 0.123)로 줄어드는 것은 감수한 비용이 아니라
**경계를 지키기로 한 선택의 불가피한 대가**다. 범위와 표준편차를 동시에 맞출 수는 없다.
이는 판단이 아니라 증명 가능한 사실이다 — i.i.d. 노이즈의 차는 특성함수가
|φ(t)|² ≥ 0이라 항상 비음수인데, 균등분포의 특성함수 sin(wt)/(wt)는 음수 구간을 갖는다.
**어떤 i.i.d. 항목별 노이즈로도 균등한 차 분포를 만들 수 없다.**

### 3-2. 클러스터-대표필지 최소거리 사전 계산

```ts
const minDistToRep = new Map<Parcel[], number>();
for (const cluster of clusters) { /* 1회 계산 */ }
clusters.sort((a, b) => {
  const da = minDistToRep.get(a) ?? Infinity;
  const db = minDistToRep.get(b) ?? Infinity;
  return (da - db) || 0;   // NaN·Infinity-Infinity를 동순위로 흡수
});
```

`Math.min(...arr)` 스프레드를 루프로 바꿨다. 봉화군 규모에서는 성능 이득이 없지만
(210ms → 204ms), 비교자에서 부수 계산을 걷어내 정렬을 순수 함수로 만드는 것이
3-1과 같은 성격의 정리다. `repProximity`의 스프레드도 함께 걷어냈다.

`|| 0`은 code-reviewer의 지적이다. 좌표에 NaN이 섞이면 `min`이 `Infinity`로 남고
`Infinity - Infinity = NaN`이 되어 **이 커밋이 고치려던 정렬 계약 위반이 재발한다.**
구 코드도 `Math.min(NaN, …) = NaN`으로 같았으므로 회귀는 아니지만, 이 줄을 이미
만졌고 최근 커밋이 좌표 생성 경로(`computePolygonCentroid`)를 손댔으므로 방어한다.

### 3-3. 가중치를 루프 밖으로 + 이름 충돌 해소

`repWeight` / `densityShare` / `noiseWeight`는 클러스터와 무관한 상수인데 루프 안에
있어 "클러스터마다 달라지는 값"처럼 읽혔다. 루프 밖으로 올렸다.

또 지역 변수 `densityWeight`(밀집도 대 대표필지 근접도의 배분)와
`spatialConfig.densityWeight`(점수 대 노이즈의 배분)가 세 줄 간격으로 놓여 있었다.
전자를 `densityShare`로 개명했다.

제목 "추출 재현성 복구"는 실제 문제를 절반만 짚는다. 정확히는 **정렬 계약 위반 해소**이고,

재리뷰가 시뮬레이션으로 확인한 것: **`densityWeight = 0`이 이제 실제로 "완전 랜덤"이다.**

## 7. 남은 것

- **과거 시드 재현 불가.** rng 소비량이 `~n log n` → `n`으로 바뀌면서 이후 모든
  `shuffle`이 다른 난수를 받는다. 어떤 올바른 수정으로도 피할 수 없지만,
  `randomSeed` 입력란의 존재 자체가 "시드를 적어두면 재현된다"는 약속이므로
  **내보내기에 알고리즘 버전을 함께 찍는 것**이 맞다(후속 티켓).
- 이 수정을 못 박는 **테스트가 없다.** Vitest 도입(PROJ1-1-9) 후 ① 동일 시드 재현성
  ② `scored`의 rank 내림차순 ③ NaN 좌표 클러스터 방어를 회귀 테스트로 고정한다.
- `calculateDensity`가 `withCoords` 전체를 매번 훑는다(`O(n²)` 소지). 이번 범위 밖.
