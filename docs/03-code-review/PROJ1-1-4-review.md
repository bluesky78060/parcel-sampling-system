# PROJ1-1-4 검증 — 엑셀 파싱 결함

작성일: 2026-09-04
대상: `src/lib/excelParser.ts`, `src/lib/extractionAlgorithm.ts`, `src/components/ColumnMapper/ColumnMapper.tsx`

## 1. 티켓의 두 진단이 모두 실제와 달랐다

두 실사용 파일의 전 시트를 훑어 컬럼명과 값 형식을 측정했다.

| 티켓의 주장 | 실측 |
| --- | --- |
| 면적에 천단위 구분자가 있어 `MIN_AREA` 필터가 정상 필지를 대량 제외 | **쉼표 0건.** 2027원본(31,070행 + 9,739행)·2026 토양검정(전 시트) 모두 `"279"`, `"3947"` 형태 |
| `직불신청_PNU`(대문자)가 `PNU_COLUMN_NAMES`에 없다 | **그 컬럼 자체가 없다.** 실제 컬럼은 `PNU`(2027)와 `BASEPNU`(2026) |

### 그러나 두 번째는 더 나쁜 형태로 실재했다

`PNU_COLUMN_NAMES = ['직불신청_pnu', 'pnu', 'PNU', '필지고유번호', 'pnu코드']`

- `PNU`는 목록에 있어 감지된다
- **`BASEPNU`는 목록에 없다** → 2026 파일은 명시 매핑 없이는 PNU를 전혀 못 잡는다

조회가 대소문자 구분 정확 매칭이라 `pnu`와 `PNU`를 따로 나열해야 했고, 그러고도
`BASEPNU` 같은 접두형은 걸리지 않았다.

## 2. 조치

### 2-1. 컬럼명 정규화 매칭

```ts
function normalizeColumnName(name: string): string {
  return name.toLowerCase().replace(/[\s_]/g, '');
}
```

행의 키를 정규화한 Map을 만들어 조회한다. 대소문자·공백·밑줄 차이를 흡수하므로
`PNU` / `pnu` / `BASEPNU` / `직불신청_PNU`가 모두 걸린다. 목록에서 중복 항목
(`'pnu'`, `'PNU'`)을 지우고 `'basepnu'`를 넣었다.

`ColumnMapper.tsx`의 자동 매핑 키워드에도 `basepnu`를 추가해 두 경로를 맞췄다.

### 2-2. 면적 파싱 방어

```ts
function parseArea(value: unknown): number | undefined {
  if (value == null || value === '') return undefined;
  const n = parseFloat(String(value).replace(/,/g, ''));
  return Number.isFinite(n) ? n : undefined;
}
```

현재 파일에는 구분자가 없지만, 걸리면 `"1,234"` → `1`이 되어 `MIN_AREA`(500㎡)
필터가 정상 필지를 대량으로 걷어낸다. `getParcelArea`의 rawData 폴백 경로
(`extractionAlgorithm.ts`)도 같은 문제를 가지고 있어 함께 고쳤다.

### 2-3. 면적 0 처리 — 초안을 되돌렸다

초안에서는 `parseArea`가 0을 보존하도록 바꾸고 "하류 동작은 달라지지 않는다"고 적었다.
**절반만 맞았다.** 리뷰가 `p.area`를 읽는 지점을 전수 조사해 조건이 갈린다는 것을 짚었다.

| 위치 | 조건 | 0 유입 시 |
| --- | --- | --- |
| `extractionAlgorithm.ts` `getParcelArea` | `p.area > 0` | 변화 없음 |
| `excelExporter.ts:155` | `p.area != null ? p.area : rawData 폴백` | **폴백이 막힘** |
| `extractionStore.ts:226` | `merged.area == null && pub.area != null` | **마스터 면적 상속 차단** |
| `excelExporter.ts:245` | `p.area ?? ''` | 빈칸 → `0` |

그리고 실측하니 **2027 파일에 면적 0값이 63건 실재한다**(원본 48 + 원본2 15).
납품 시트에 0이 찍히고 rawData 폴백이 막히는 회귀가 된다.

0을 부적격으로 볼지 정보 없음으로 볼지는 업무 결정이고 소비 지점 두 곳을 함께
손봐야 한다. **검증된 변경(쉼표 방어)에 미검증 정책 변경을 섞지 않기 위해**
0 보존을 되돌렸다. 후속 과제로 남긴다.

### 2-4. 빈 중복 컬럼이 유효 값을 덮던 회귀 — 내가 만든 것

초안의 정규화 Map은 무조건 덮어쓰기였다.

```
{PNU:'479…', pnu:''}  →  초안: undefined  |  HEAD: '479…'
```

`parseExcelSheets`가 다중 시트를 합칠 때 헤더 합집합을 채우느라 없는 컬럼에 `''`를
자기 키 **뒤에** 붙이므로(`:112-115`), 시트마다 PNU 표기가 다르면 정확히 이 형태가
만들어진다. 발동하면 **이번 티켓이 고치려던 증상이 그대로 재발한다.**

빈 값이 유효 값을 이기지 못하도록 고쳤다(non-empty-wins).

실측: 두 파일의 헤더 정규화 충돌은 2026 파일의 `OM`/`　OM　`, `Mg`/`mg`
(토양 성분) 두 쌍이다. PNU 키에는 충돌이 없지만 충돌 자체는 실재한다.

### 2-5. `PNU`와 `BASEPNU` 우선순위 — 두 번 고쳤다

초안은 `basepnu`를 `pnu`보다 앞에 뒀다. `BASEPNU`가 분할 전 모(母)필지 PNU를
뜻한다면 좌표가 옆 필지로 붙어도 "100% 변환 성공"으로 보이므로, 정본인 `pnu`가
앞에 와야 한다. 두 목록 모두 순서를 바로잡았다.

**그런데 `ColumnMapper` 쪽은 순서를 바꿔도 아무 일도 일어나지 않는다.**
재리뷰가 `autoMatch`의 루프 중첩을 짚었다.

```ts
for (const header of headers) {   // ← 헤더가 바깥
  for (const kw of keywords) {    // ← 키워드가 안쪽
```

**어떤 키워드든 처음 맞는 '헤더'가 이긴다.** 키워드 목록 내부 순서는 결과에
영향이 없다. 즉 순서 조정은 무의미했고, `'basepnu'`를 목록에 넣은 행위 자체가
HEAD 대비 선택을 `PNU` → `BASEPNU`로 뒤집고 있었다 — 같은 커밋의 주석이 선언한
정책과 정반대다.

`autoMatch`에는 2차 부분 매칭이 있고 `BASEPNU`.includes(`pnu`)가 참이므로,
**`'basepnu'`를 빼도 2026 파일은 그대로 잡힌다.** 그러면서 `PNU`가 있을 때는
1차 정확 매칭으로 그쪽이 선택된다. 최소 개입으로 정책과 동작을 맞췄다.

실측: 두 컬럼이 **한 시트에 공존하는 경우는 없다**(2027은 `PNU`만, 2026은
`BASEPNU`만). `parseExcelSheets`는 파일 하나의 시트만 합치므로 서로 다른 파일의
헤더가 섞이지도 않는다. 현 데이터에서 실제 위험은 0이지만, 정책이 코드와
어긋난 채로 남기지 않았다.

### 2-6. 쉼표 방어를 세 곳으로 통일

재리뷰가 세 번째 지점을 짚었다. `excelExporter.ts:117`의 `getRawNum`이
`parseFloat(v)`를 그대로 쓰고 있었고, 이 함수는 `p.area`가 없을 때
**납품 시트의 재배면적 칸**을 채운다. 서식이 걸린 셀이 들어오면 선정 필터가
아니라 산출물이 틀어지므로 더 조용하고 나쁜 실패다.

같은 로직이 세 곳에 흩어져 있어 `parseNumericCell`로 모으고 셋 다 그것을 쓴다.
다음번에 또 한 곳이 누락되는 것을 막는다.

## 4. 영향

PNU를 놓치면 중복 감지가 주소 폴백으로 떨어지고, **PROJ1-1-20에서 도입한 PNU 우선
좌표 변환(Phase 0)이 통째로 동작하지 않는다.** 2026 파일을 마스터로 쓰는 경우가

## 5. 남은 것

- **면적 0의 의미** — 부적격으로 볼지 정보 없음으로 볼지 업무 결정 필요.
  실데이터에 63건 존재하며, 살리려면 `excelExporter.ts:155`와
  `extractionStore.ts:226`을 함께 손봐야 한다. → PROJ1-1-24
- **`BASEPNU`의 의미 확인** — 분할 전 모필지 PNU라면 그 좌표는 옆 필지를 가리킨다.
  표본 20건의 PNU 좌표와 주소 지오코딩 좌표의 거리를 비교하면 판별된다.
  변환율은 정합성을 증명하지 않는다.
- **`autoMatch`의 키워드 우선순위가 작동하지 않는다.** 루프 중첩이 헤더 바깥/
  키워드 안쪽이라 목록 순서가 무의미하다. 뒤집으면 전 필드에 영향이 가므로
  이번에는 손대지 않았다(2-5 참조).
- `extractPnu`가 행마다 정규화 Map을 만든다. 31,070행 × 42컬럼에서 174ms
  (기존 4ms, 43배). `applyColumnMapping`이 최대 4회 호출되어 최악 0.7초.
  당장 고칠 수준은 아니나 헤더가 같으므로 1회만 만들면 된다.
- 이 수정을 못 박는 테스트가 없다. Vitest 도입(PROJ1-1-9) 후
  ① `BASEPNU` 컬럼만 있는 행에서 `extractPnu`가 값을 반환하는지
  ② `parseArea("1,234") === 1234`
  ③ **`{PNU:'479…', pnu:''}`가 값을 반환하는지** (2-4의 회귀 방지)
  를 회귀 테스트로 고정할 것.
